# Compiling Avro Schemas: Inside the Generated Java Class

Most tutorials treat code generation as a black box: run the plugin, import the class, move on. That works until the class surprises you. A getter returns `CharSequence` where you expected `String`, a nullable field turns into `Integer` instead of `int`, or someone edits the generated file and loses the change on the next build. Every one of those surprises is written plainly in the generated source, if you open it.

This guide follows the [Compiling the schema](https://avro.apache.org/docs/++version++/getting-started-java/#compiling-the-schema) step of Apache Avro 1.12.2's Getting Started (Java) guide, then opens the `User` class the compiler produces and reads it section by section: the embedded schema, the fields and their Java types, the accessors, the builder and the custom coders. It finishes with `CompilingTheSchemaTest`, five JUnit 6 tests that pin down what the generator promises.

## What is Avro Code Generation?

Code generation turns a schema into a Java class with one field per schema field, typed accessors, a builder, and the schema embedded as a constant. The Avro documentation calls this **specific** data, as opposed to **generic** data, where records are maps from field names to values ([section 1.7](07-avro-without-code-generation.md)).

Generated classes give you three things the generic API doesn't:

- **Compile-time checking.** `user.setFavoriteNumber("seven")` doesn't compile.
- **IDE support.** Autocompletion shows you the fields of the schema.
- **Speed.** Generated classes can encode and decode themselves without looking up fields by name ([section 1.8](08-faster-avro-serialization-with-custom-coders.md)).

The cost is a build step, and a class that must be regenerated whenever the schema changes.

## Compilation Overview

From schema file to class you can use, the flow is:

1. **Maven reaches `generate-sources`**, the phase before `compile`.
2. **The `avro-maven-plugin` runs its `schema` goal** on every `.avsc` file in its source directory.
3. **The compiler writes one Java file per named type**, in a package taken from the namespace: `example/avro/User.java`.
4. **The plugin adds the output directory to the compile sources**, so `javac` compiles `User.java` with your own code.
5. **Your code imports `example.avro.User`** like any other class.

## Two Ways to Compile

### With avro-tools

The guide first shows the command-line tool:

```bash
java -jar /path/to/avro-tools-1.12.2.jar compile schema user.avsc .
```

That writes `example/avro/User.java` under the current directory. It is handy for a quick look at what a schema produces, but nothing reruns it when the schema changes.

### With the Maven Plugin

The course uses the plugin, so every build regenerates the class. [Section 1.1](01-setting-up-an-avro-maven-project.md) explains the configuration; the essential part is:

```xml
<plugin>
    <groupId>org.apache.avro</groupId>
    <artifactId>avro-maven-plugin</artifactId>
    <executions>
        <execution>
            <phase>generate-sources</phase>
            <goals>
                <goal>schema</goal>
            </goals>
            <configuration>
                <sourceDirectory>${project.basedir}/src/main/resources/avro/</sourceDirectory>
            </configuration>
        </execution>
    </executions>
</plugin>
```

One deliberate difference from the guide: the guide sets `<outputDirectory>` to `src/main/java`, which puts the generated file among your own sources. The course leaves it at the default, `target/generated-sources/avro`, so the class is build output that `mvn clean` deletes and nobody commits or edits.

## Inside User.java

### The Warning at the Top

```java
/**
 * Autogenerated by Avro
 *
 * DO NOT EDIT DIRECTLY
 */
```

Take this literally. The next build overwrites the file. If you need behaviour on top of a generated class, wrap it or write a helper; to change the class itself, change the schema or the plugin configuration.

### The Embedded Schema

```java
public static final org.apache.avro.Schema SCHEMA$ = JsonSchemaParser.parseInternal("{\"type\":\"record\",\"name\":\"User\", ...");
```

The argument is the compact JSON from [section 1.2](02-defining-an-avro-schema.md), so the class carries its own schema. `getClassSchema()` returns it statically, and `getSchema()` returns it from an instance. That is how a `DataFileWriter` knows what to write in the file header without you passing it a schema file.

Next to it the class holds a `SpecificData` model and a static binary encoder and decoder:

```java
private static final SpecificData MODEL$ = new SpecificData();
private static final BinaryMessageEncoder<User> ENCODER = new BinaryMessageEncoder<>(MODEL$, SCHEMA$);
private static final BinaryMessageDecoder<User> DECODER = new BinaryMessageDecoder<>(MODEL$, SCHEMA$);
```

Those back `toByteBuffer()` and `fromByteBuffer(..)`, the single-object encoding covered in Module 6.

### The Fields and Their Java Types

```java
private java.lang.CharSequence name;
private java.lang.Integer favorite_number;
private java.lang.CharSequence favorite_color;
```

Two mappings deserve attention:

- **`["int", "null"]` becomes `Integer`**, not `int`, because a primitive can't hold `null`. A required `int` would become `int`.
- **`string` becomes `CharSequence`.** The guide's configuration doesn't set the plugin's `stringType`, so the default applies. When Avro reads a string, it gives you its own `org.apache.avro.util.Utf8`, which is a `CharSequence` but not a `String`. [Section 1.6](06-deserializing-avro-data-files.md) shows what that means for `equals`; Module 3 sets `stringType` to `String`.

### The Accessors

Field names in the schema use snake case; the accessors use Java camel case:

```java
public java.lang.Integer getFavoriteNumber() { return favorite_number; }
public void setFavoriteNumber(java.lang.Integer value) { this.favorite_number = value; }
```

The private fields keep the schema's names (`favorite_number`), so the class lines up with the schema, while your code reads like Java.

### The Builder

`User.newBuilder()` returns a nested `User.Builder` that tracks which fields were set. Its `build()` method shows how a missing field is handled:

```java
public User build() {
  try {
    User record = new User();
    record.name = fieldSetFlags()[0] ? this.name : (java.lang.CharSequence) defaultValue(fields()[0]);
    record.favorite_number = fieldSetFlags()[1] ? this.favorite_number : (java.lang.Integer) defaultValue(fields()[1]);
    record.favorite_color = fieldSetFlags()[2] ? this.favorite_color : (java.lang.CharSequence) defaultValue(fields()[2]);
    return record;
  } catch (org.apache.avro.AvroMissingFieldException e) {
    throw e;
  } catch (java.lang.Exception e) {
    throw new org.apache.avro.AvroRuntimeException(e);
  }
}
```

For each field: if it was set, use the value; otherwise ask the schema for the default. Because no field in `user.avsc` has a default, an unset field ends in an `AvroMissingFieldException`. [Section 1.4](04-creating-avro-records-in-java.md) shows the exact message.

### The Custom Coders

At the end of the class are `customEncode(..)` and `customDecode(..)`, and `hasCustomCoders()` returns `true`. They write each field directly, without looking anything up in the schema. Avro uses them only when a beta flag is switched on, which is the subject of [section 1.8](08-faster-avro-serialization-with-custom-coders.md).

## Testing What the Generator Promises

Reading generated code once is useful; pinning it down with tests is better, because a plugin upgrade or a configuration change then shows up as a failing test instead of a surprise. `CompilingTheSchemaTest` uses reflection for the shape of the class and `SchemaParser` for the embedded schema:

```java
class CompilingTheSchemaTest {

    @Test
    void fieldNamesBecomeCamelCaseAccessors() throws NoSuchMethodException {
        // favorite_number in the schema; getFavoriteNumber and setFavoriteNumber in Java.
        assertThat(User.class.getMethod("getFavoriteNumber")).isNotNull();
        assertThat(User.class.getMethod("setFavoriteNumber", Integer.class)).isNotNull();
        assertThat(User.class.getMethod("getFavoriteColor")).isNotNull();
    }

    @Test
    void aNullableIntIsABoxedInteger() throws NoSuchMethodException {
        // ["int", "null"] can hold null, so it can't be a primitive int.
        assertThat(User.class.getMethod("getFavoriteNumber").getReturnType()).isEqualTo(Integer.class);
    }

    @Test
    void stringsAreCharSequencesByDefault() throws NoSuchMethodException {
        assertThat(User.class.getMethod("getName").getReturnType()).isEqualTo(CharSequence.class);
    }

    @Test
    void theClassEmbedsItsSchema() {
        assertThat(User.SCHEMA$).isSameAs(User.getClassSchema());
        assertThat(new User().getSchema()).isSameAs(User.SCHEMA$);
    }

    @Test
    void theEmbeddedSchemaIsTheSchemaInTheFile() throws IOException {
        assertThat(User.getClassSchema())
            .isEqualTo(new SchemaParser().parse(new File("src/main/resources/avro/user.avsc")).mainSchema());
    }
}
```

The last test is the important one: it proves the class and the file agree. If someone changed `User.java` by hand instead of the schema, or the build used a stale copy, this is where it would show.

## Common Pitfalls

1. **Editing the generated file.** The guide's `outputDirectory` of `src/main/java` makes this tempting, because the file sits next to your code. Keep generated code in `target/`, where it's obviously build output.
2. **Expecting `String`.** `getName()` returns `CharSequence`, and after reading it's a `Utf8`. Comparing it with `"Ben"` using `equals` is `false`. Call `toString()`, or configure `stringType`.
3. **Expecting `int` for a nullable number.** Unboxing a `null` `Integer` throws a `NullPointerException`. Check for `null`, or give the field a non-null type and a default.
4. **Schema changes that don't show up.** The plugin only runs in `generate-sources`. Running a test from the IDE without a Maven build can use an old `User` class. When in doubt, run `mvn clean test`.
5. **Forgetting that the namespace is the package.** Changing `"namespace"` moves the class to another package and breaks every import, and in Avro 1.12.2 it also changes which package you must trust for reading ([section 1.6](06-deserializing-avro-data-files.md)).

## Wrapping Up

The compiler turns `user.avsc` into a class that carries its schema, maps every field to a Java type you can predict (`CharSequence` for strings, `Integer` for a nullable int), and adds accessors, a validating builder and fast custom coders. Generated in `target/generated-sources/avro` on every build, it can't drift from the schema, and a test comparing `User.getClassSchema()` with the file proves it.
